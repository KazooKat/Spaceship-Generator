# Troubleshooting

Quick reference for common errors when running the spaceship generator. Companion to [quickstart.md](quickstart.md) — if a command in the quickstart fails, check the table below first.

## Common errors

| Symptom | Cause | Fix |
|---|---|---|
| `Palette 'NAME' not found at .../palettes/NAME.yaml` | The palette name passed to `--palette` does not match any YAML in `palettes/`. | Run `spaceship-generator --list-palettes` to print every available name (or browse [palettes.md](palettes.md)), then re-run with one of those. |
| `argument --hull-style: invalid choice: 'X'` (or `--engine-style` / `--wing-style` / `--cockpit`) | The shape-style value is not a member of the corresponding enum. | Run `spaceship-generator --list-shape-styles` to see every `HullStyle` / `EngineStyle` / `WingStyle` member. |
| `argument --greeble-style: invalid choice: 'X'` | The greeble type is not a `GreebleType` enum member. | Run `spaceship-generator --list-greeble-types` for the bare value list. |
| `argument --weapon-type: invalid choice: 'X'` (or unknown values warned by `--weapon-types`) | The weapon-type token is not a `WeaponType` enum member. | Run `spaceship-generator --list-weapon-types` for the bare value list. |
| `--no-weapons and --weapon-count are mutually exclusive` | Both flags were passed in one invocation. | Drop one — `--no-weapons` is the shortcut for `--weapon-count 0`. |
| `--no-greebles and --greeble-density are mutually exclusive` | Both flags were passed in one invocation. | Drop one — `--no-greebles` is the shortcut for `--greeble-density 0`. |
| `--stats and --stats-json are mutually exclusive` | Both stat flags were passed. | Drop one — `--stats-json` is the machine-readable variant of `--stats`. |
| `--output - is single-ship only; mutually exclusive with --repeat, --fleet-count, --seeds` | Stdout-streaming mode only supports one ship per invocation. | Drop the bulk-mode flag, or write to a directory with `--out PATH` instead of `--output -`. |
| `--ship-size: W>=4, H>=4, L>=8 required` | Dimensions below the `ShapeParams` floor. | Pass dimensions that meet the minimums (e.g. `--ship-size 8x6x16`). |
| `argument --greeble-density: must be in [0.0, 1.0]` | Greeble density is a unit float. | Pass a value in `[0.0, 1.0]`. |
| `--seeds range must be 'A-B' with integers` (or `must not be empty`) | Malformed `--seeds` value — accepts comma-list, inclusive range, or mix. | Use `--seeds 1,2,3`, `--seeds 0-9`, or `--seeds 1,3-4,9`. |
| Web UI returns HTTP 429 with `{"error": "rate_limited"}` | Per-IP fixed-window rate limit was hit on a `POST /generate` / `/api/generate` / `/api/batch` / `GET /preview-lite` / `/download-fleet` request. | Wait `Retry-After` seconds, or tune via env vars `SHIPFORGE_RATE_LIMIT` (default 30) and `SHIPFORGE_RATE_WINDOW` (default 60s) — see [web_ui.md](web_ui.md). |
| `ModuleNotFoundError: No module named 'flask'` (or `jsonschema`, `PIL` / `Pillow`) | Optional dependency not installed in the active environment. | `pip install -e .[dev]` to pick up the dev extras, or install just the missing package (e.g. `pip install flask`); `jsonschema>=4.0` is also pinned in `requirements-dev.txt`. |
| `presets unavailable` / `weapon_styles unavailable` warning on stderr | Optional submodule failed to import (partial install or in-progress refactor). | Re-install the package with `pip install -e .` from the repo root; the CLI still runs without these but `--preset` / `--weapon-*` flags will no-op. |
| `unrecognized arguments: --list-engine-styles` (or any of the per-component `--list-*-styles[-json]` flags) | The per-component list flags (`--list-hull-styles`, `--list-engine-styles`, `--list-wing-styles`, plus their `-json` siblings, and `--version-json`) shipped in cycle 2 of 2026-05-07 — older installs only expose the bundled `--list-shape-styles[-json]`. | Run `spaceship-generator --version` (or `--version-json` for tooling) to see the installed version; if it predates the cycle-2 release, `pip install -e .` from the repo root or upgrade the package. See [cli.md](cli.md) for the full sibling pack. |
| `bench_*.py --csv` output is empty (or interleaved with banner text) when piping | The `--csv` mode splits streams: CSV goes to **stdout**, the run-banner + per-iter progress lines go to **stderr** (see [bench.md](bench.md)). Folding stderr into stdout (`2>&1`) corrupts the CSV document. | Drop the `2>&1`: `python scripts/bench_summary.py --csv > out.csv` is correct, `python scripts/bench_summary.py --csv > out.csv 2>&1` is wrong. To capture both streams separately, use `... --csv > out.csv 2> out.log`. |
| `palette_stats.py` reports fewer palettes than `ls palettes/` shows | `scripts/palette_stats.py` reuses the strict palette loader; palettes that fail to parse are silently dropped from the corpus stats so a single broken file doesn't poison the aggregate. | Run `python scripts/palette_lint.py --all --strict` to surface the offenders — every dropped palette will appear with one or more `error:` / `warn:` lines pointing at the offending YAML. |
| `GET /api/version` returns `{"version": "0.0.0+unknown"}` | The route uses `importlib.metadata.version("spaceship-generator")`, which returns the editable-install fallback when the package was installed with `pip install -e .` in some environments (no installed `.dist-info`). | Re-install non-editable (`pip install .`) for a release-tagged build, wait for the next release tag, or read `__version__` from the package directly (`python -c "import spaceship_generator; print(spaceship_generator.__version__)"`). See [web_ui.md](web_ui.md) for the route. |
| `palette_diff.py` shows `<missing>` for a role | The role is defined in only one of the two palettes; `scripts/palette_diff.py` treats absent roles as gaps rather than errors, since palettes legitimately diverge on optional roles. | To see which roles are MANDATORY (and would therefore be a real defect when missing) run `python scripts/palette_lint.py --strict` against each palette — strict mode surfaces every missing required role. |
| Cross-axis property test fails with one specific `(style_a, style_b, seed)` tuple | One member-pair × seed combination in a `tests/test_properties.py::test_property_*_cross_*` parametrize grid hit a regression — the failure node ID self-names the offending tuple. | Reproduce with `pytest tests/test_properties.py -k "<test_name> and <style_a>-<style_b>-<seed>"`, then inspect the resulting `.litematic` size / contents (the test writes to `tmp_path` — print it from the test, or re-run the same `generate()` call locally with the same seed). |
| `palette_search.py --block <id>` prints "0 hit(s)" and exits 1 | The `--block` value did not match any palette role in `palettes/`. Two common causes: (a) the bare block id was passed without the `minecraft:` namespace prefix, which never matches because the corpus stores every block as a fully-qualified `namespace:id` string; (b) the block really is unused — `palette_search.py` deliberately exits 1 on no-hits so CI / shell pipelines can branch on `$?` (exit 0 = at least one hit, exit 1 = no hits / missing `palettes/`, exit 2 = bad CLI args). | Re-run with the full id (`python scripts/palette_search.py --block minecraft:stone`, not `--block stone`); blockstate suffixes (`[axis=y]`) are stripped before comparison so `minecraft:oak_log` matches `minecraft:oak_log[axis=y]` too. If the exit-1 is intentional in CI, treat it as a "no callers" signal rather than a failure. |
| `palette_search.py --block <id>` prints dozens / hundreds of hits | The block is a *common* role across the corpus (e.g. `minecraft:stone`, `minecraft:white_concrete` typically appear in 20+ palettes). The fixed-width text table is hard to scan at that size. | Re-run with `--csv` to get a parseable `palette,role` stream you can pipe into `sort` / `uniq -c -f1` / a spreadsheet (`python scripts/palette_search.py --block minecraft:stone --csv > hits.csv`); banner lines route to stderr in `--csv` mode so stdout stays clean. If you want palettes that use the block in a *specific* role only, filter the CSV on column 2 (e.g. `awk -F, '$2=="HULL"' hits.csv`). |
| Can't find the per-`StructureStyle` override list (engine count, wing prob, hull rx/ry, etc.) in `docs/architecture.md` | The architecture doc's `## Structure pipeline` section names the dispatch functions but doesn't enumerate every per-style numeric override (those are intentionally kept in the source so the doc can't drift). | Read `src/spaceship_generator/structure_styles.py` directly — the per-style `if style == StructureStyle.<X>: return ...` branches in `profile_fn` / `hull_rx_ry_scale` / `engine_count_override` / `engine_radius_scale` / `wing_prob_override` / `wing_size_scale` are the truth source. See [architecture.md#structure-pipeline](architecture.md#structure-pipeline) for the seam diagram. |
| Fleet `.litematic` files from one run overwrite files from a previous run in the same `--out` directory | `--fleet-count N` writes per-ship files as `ship_<seed>_<idx>.litematic` into `--out` (default `out/`). Re-running with the same `--seed` (or picking the same fleet seed at random) into the same `--out` regenerates the same filenames, so the old `.litematic` files are silently overwritten. | Either pass a different `--out` directory per fleet run (`--out fleets/run-2026-05-08/`), pass an explicit `--seed` you don't reuse, or move/rename the previous run's files before re-invoking. Fleet runs only collide *with each other*; the per-ship `_<idx>` suffix prevents within-fleet collisions. |
| Authoring a new palette and a YAML edit causes a silent failure (missing role, bad block id, role typo, indent error) | The runtime palette loader is tolerant — many authoring mistakes don't surface until generate-time as silent no-op blocks or missing-block errors at Litematica load. | See [palette_authoring.md#common-pitfalls](palette_authoring.md#common-pitfalls) for the five mistakes new authors hit most often, and run `python scripts/palette_lint.py --strict <palette.yaml>` (or `--all --strict` for the whole `palettes/` corpus) — that's the canonical "catches this" tool for everything in that pitfalls list. |
| `--meta-json and --output are mutually exclusive` (or `--output-json` / `--output-json-schema` / `--config-dump`) — exit code 2, message printed to stderr | `--meta-json` is a discovery / metadata short-circuit (emits the combined enum/palette/preset/version JSON document and exits before any ship is generated), so it's mutually exclusive with every flag that produces a generated-ship payload (`--output`, `--output-json`, `--output-json-schema`) and with the other discovery short-circuit (`--config-dump`). The mutex is enforced via `parser.error` → exit 2 + diagnostic on stderr. | Drop one — use `--meta-json` alone for tooling discovery, `--config-dump` alone to inspect the effective generator config, or one of the `--output*` flags alone to generate a ship. See [cli.md#machine-readable-list--output-flags](cli.md#machine-readable-list--output-flags) for the full mutex matrix. |
| `palette_lint.py --json` output doesn't match the consuming tool's expected shape (e.g. `jq '.[].name'` returns `null`) | `scripts/palette_lint.py` ships **two** JSON output flags with different schemas: `--format json` (legacy, per-palette `{name, path, errors, warnings}`) and `--json` (newer, per-palette `{palette, ok, errors, warnings}` with the `ok` boolean). They are not interchangeable — `--format json` has no `ok` field, `--json` renames `name`→`palette` and drops `path`. | Pick the schema your consumer expects: use `--json` for CI gates that branch on `.ok` (`jq -r '.ok'` for `--file`, `jq -r '.[].ok'` for `--all`); use `--format json` for tools written against the original schema. Both forms support `--strict` (warnings count toward the failure flag). |
| Texture pattern flags (`--window-period`, `--stripe-period`, `--rivet-period`, `--belly-light-period`) appear silently ignored on small ships | Each period is clamped to a minimum of 2 inside `texture.py` (`period = max(2, params.<period>)`), so values `0` and `1` silently behave as `2`. At the upper end the threshold is implicit: when a period exceeds the relevant ship-axis length, the `_z_phase_mask` / `_y_band_mask` produces zero hits, so the pass becomes a silent no-op (no error, no warning — the resulting `.litematic` just lacks that texture pass). | Pick periods in `[2, ship_axis_length / 2]` so at least two repeats land — for a `--ship-size 8x6x16` ship that means `--window-period` / `--stripe-period` ≤ 8. To verify a period actually fires, render once with the default and once with the chosen value and compare `--stats-json`'s per-role block counts; a no-op period leaves `WINDOW` / `HULL_DARK` / `LIGHT` counts unchanged. See [architecture.md#texture-pipeline](architecture.md#texture-pipeline) for the per-pass period semantics. |
| `--output-json \| jq` fails with `parse error: Invalid numeric literal` (or similar) when stderr is folded into stdout via `2>&1` | The CLI splits streams: the JSON payload from `--output-json` goes to **stdout**, while progress / banner / warning lines (e.g. `presets unavailable`, palette-load notices) go to **stderr**. Folding stderr into stdout (`... --output-json 2>&1 \| jq .`) interleaves non-JSON text into the document, which `jq` then refuses to parse. Same convention as the `bench_*.py --csv` family. | Drop the `2>&1` — `python -m spaceship_generator --output-json ... \| jq .` is correct. To capture both streams, route them separately: `python -m spaceship_generator --output-json ... > out.json 2> out.log`, then `jq . out.json`. See [output-formats.md#consumer-examples](output-formats.md#consumer-examples) for the canonical jq pipeline. |
| Re-running the same `--seed --fleet-count N --out DIR` produces identical filenames that overwrite the previous run's `.litematic` files | Fleet runs are fully deterministic — the per-ship seeds are pulled from a single `random.Random(--seed)` stream inside `fleet.py`, so the same master `--seed` produces the same per-ship seed sequence and therefore the same `ship_<seed>_<idx>.litematic` filenames every time. The on-disk collision is not a fleet bug; it's the same overwrite behavior the single-ship `--seed` case has when writing into the same `--out`. | If you want each fleet run preserved, use a per-run `--out` directory (`--out fleets/run-2026-05-08/`, `fleets/run-2026-05-09/`, ...) or move/rename the previous run's files first. If you want a *different* fleet from the same `--out`, change `--seed`. See [architecture.md#fleet-pipeline](architecture.md#fleet-pipeline) for the per-ship seed derivation. |
| Two palette packs ship the same palette name (e.g. both define `palettes/desert_oasis.yaml`) and one silently masks the other | `list_palettes()` in `palette.py` enumerates `palettes_dir().glob("*.yaml")` and uses each path's `stem` as the canonical name — there is no namespacing across packs, so if a vendored pack and a hand-authored YAML share a stem the filesystem entry that wins is whatever the glob returns first (filesystem-order dependent, NOT alphabetical-precedence rules). `--list-palettes` shows the surviving name exactly once with no warning, which is what makes the collision look like a missing palette rather than a duplicate. | Run `python -c "from pathlib import Path; from collections import Counter; print({k:v for k,v in Counter(p.stem for p in Path('palettes').glob('*.yaml')).items() if v>1})"` to surface every stem with `>1` YAML behind it; or `ls palettes/*.yaml \| awk -F/ '{print $NF}' \| sort \| uniq -d` on a POSIX shell. Then rename one of the colliding files (e.g. `desert_oasis_packA.yaml` vs `desert_oasis_packB.yaml`) so `--list-palettes` enumerates both. |
| Adding a new `(axisA × axisB)` cross-axis property test triggers `pytest` collection errors like `duplicate test ID` or `In test_property_<X>_x_<Y>_seed_grid: error parametrize ids` | Every cross-axis test in `tests/test_properties.py` builds parametrize IDs from the enum `.value` (or numeric repr) of each axis member — if the new pair reuses an `(axisA_member, axisB_member, seed)` tuple that an *existing* cross-axis grid in the same module already enumerates (e.g. adding `hull × wing` after `hull × engine` and `engine × wing` both already pin the same hull/wing members at the same seed), pytest refuses to collect the duplicate node ID. | Either (a) widen the new grid's seed pool away from the shared seeds in `_SHAPE_STYLE_STABILITY_SEEDS = [0, 1, 7]` for the overlapping axis-pair, or (b) prefix the new test's parametrize `ids=` factory with the new axis-pair name (`ids=lambda v: f"{NEW_PAIR}-{v}"`) so the node ID is namespaced. Run `pytest tests/test_properties.py --collect-only -q \| sort \| uniq -d` to enumerate every duplicate ID before debugging individual cases. |
| `python scripts/palette_lint.py --json --all \| jq '.[] \| select(.ok==false)'` works on bash but fails on Windows PowerShell with parse errors / empty output | PowerShell has two quoting pitfalls jq pipelines hit: (a) single-quoted jq filters like `'.[] \| select(.ok==false)'` are parsed by PowerShell first — single quotes preserve the string but `\|` inside is still a PowerShell pipe so the filter gets split across two commands; (b) double-quoted `"…"` strings expand `$` so a filter like `".name"` becomes empty (no PS variable `$name`). | Use the PowerShell stop-parsing token to hand the rest of the line straight to the child process verbatim: `python scripts/palette_lint.py --json --all --% \| jq ".[] \| select(.ok==false)"` (everything after `--%` is shipped to the executable unmodified). Alternatively, escape the literal `$` with a backtick (`` `$ ``) inside double-quotes, or wrap the jq filter in single quotes AND escape PS metacharacters (`` ` `` before `\|`). The bash-style `\\|` single-quoted form does not work in PowerShell. |
| Architecture cross-link footer table (`## Cross-link index` at the bottom of `docs/architecture.md`) silently goes stale after a CLI flag rename (e.g. `--engine-style` → `--engine-shape`) | The cross-link table is hand-authored — there is no test asserting that every flag name in column 2 still exists in `src/spaceship_generator/cli.py`'s argparse. A rename in `cli.py` will pass `pytest -q` and `ruff check .` even though the footer now points at a dead symbol. The same applies to the per-pipeline anchor links in column 1 if a pipeline H2 is renamed. | Run a one-liner that grep-diffs every backticked flag in the footer against `cli.py`: `python -c "import re,pathlib; foot=pathlib.Path('docs/architecture.md').read_text(); cli=pathlib.Path('src/spaceship_generator/cli.py').read_text(); print([f for f in set(re.findall(r'\\-\\-[a-z][a-z0-9-]+', foot)) if f not in cli])"`. Any flag printed there is referenced in the footer but missing from `cli.py` — fix the footer (or revert the rename). Same idea for endpoint paths against `web/`. |
| `--greeble-density 0` produces ships with NO greebles at all (expected); `--greeble-density 1.0` produces ships where every surface anchor is a greeble (which can look saturated / chaotic, NOT broken) | The greeble scatter pass in `greeble_styles.scatter_greebles` treats `greeble_density` as a per-anchor probability against the candidate cell pool — `0.0` short-circuits the pass to a no-op (same effect as `--no-greebles`, see the existing mutex row) and `1.0` claims every eligible anchor. At the upper extreme this can mask other roles (window strips, panel lines) that paint after greebles via `_PROTECTED_ROLES`, so a `1.0` ship can look *less* detailed than a `0.6` one even though it has more greeble blocks. | If the output looks empty at `0`, the pass is doing what was asked — switch to `0.3`-`0.7` for a balanced ship. If the output looks saturated at `1.0`, dial back to `0.6`-`0.8` to let texture passes win the role-overwrite race; verify via `--stats-json` per-role block counts (`GREEBLE` block count grows monotonically with density, `WINDOW` / `HULL_DARK` shrinks). See [architecture.md#greeble-pipeline](architecture.md#greeble-pipeline) for the scatter pass and `_PROTECTED_ROLES` overwrite gate. |
| `--config-dump` JSON output schema silently changes (downstream `jq '.engine_style'` returns `null`) after a CLI flag rename in `cli.py` | `--config-dump` serializes the parsed argparse `Namespace` straight to JSON — the keys are derived from the argparse `dest=` (or auto-derived from the flag name with `-`→`_`), so renaming `--engine-style`→`--engine-shape` in `cli.py` flips the JSON key from `engine_style` to `engine_shape` with no test guard (no fixture pins the document shape). Same hazard for `--list-*-json` flags whose payload mirrors enum names. | Diff the live JSON keys against `cli.py` before assuming a key still exists: `python -m spaceship_generator --config-dump 2>/dev/null \| python -c "import sys,json; print(sorted(json.load(sys.stdin).keys()))"` then grep each key against `src/spaceship_generator/cli.py`. To pin the schema, snapshot a known-good `--config-dump` into `tests/fixtures/` and add a test that asserts the key set is a superset (renames will then fail loudly). |
| Replaying a saved manifest via `--from-manifest run.json` produces a *different* ship than the original (different block count, different `--stats-json` totals) even though the manifest hasn't changed | `--from-manifest` reproduces the explicit fields recorded in the manifest, but anything *not* pinned in the manifest falls back to the current preset / palette / per-style defaults at replay time. If the original run inherited a default that has since changed (preset YAML edited, palette YAML role added, `texture.py` period default bumped, new style enum member shifted the default order), the replay diverges silently — exit 0, no warning. | Pin every input explicitly on the original invocation so the manifest is self-contained: pass the preset by name *and* the palette by name *and* every shape-style flag rather than relying on defaults; re-export with `--output-json` (which dumps the *resolved* config) and replay from that instead of the leaner `--from-manifest`. To audit what drifted, diff the original `--config-dump` against a current `--config-dump` of the same flags — any key whose value changed is a candidate. |
| `palette × engine_style` cross-axis property test (`tests/test_properties.py::test_property_palette_x_engine_style_seed_grid`) fails on one specific `(palette, engine_style, seed)` tuple while the per-axis tests still pass | Two common root causes for this specific cross-axis pair: (a) the palette stubs the `ENGINE` role (or maps it to a block id the engine mesh can't paint into — e.g. a non-cube blockstate where the engine pass expects a full cube), so the per-palette test passes (other engine styles don't trigger the role) and the per-engine test passes (other palettes have a real `ENGINE` mapping); (b) an `engine_style` introduces a new sub-mesh (e.g. nacelle struts on `EngineStyle.TRIPLE`) that uses an extra role one palette doesn't define, so `palette.get(role)` returns the fallback and the resulting `.litematic` block count drifts off the parametrize-pinned expectation. | Reproduce the single node with `pytest tests/test_properties.py -k "palette_x_engine_style and <palette>-<engine_style>-<seed>"` (the parametrize ID self-names the offending tuple); then `python scripts/palette_lint.py --strict palettes/<palette>.yaml` to surface a missing/stubbed `ENGINE` role, and grep `src/spaceship_generator/structure_styles.py` for the engine-style branch to see which sub-meshes / extra roles it introduces. Fix is either to add the missing role to the palette or to widen the test grid away from the stub-role palette for that axis pair. |
| Web UI preset drawer shows no presets / hangs on load / throws `SyntaxError: Unexpected token` in DevTools console after a manual `localStorage` edit | The preset drawer reads/writes `localStorage["shipforge.presets.v1"]` (see `src/spaceship_generator/web/static/presets.js`) as a single JSON-encoded array. A malformed entry (trailing comma, unquoted key, half-pasted JSON) makes `JSON.parse` throw and the drawer fails to populate — the rest of the page still loads, but the drawer is empty and the console logs the parse error. There is no auto-recovery; the bad payload survives across page reloads. | Open DevTools → Application → Local Storage → your origin → delete the `shipforge.presets.v1` key (or run `localStorage.removeItem("shipforge.presets.v1")` in the Console), then reload — the drawer rebuilds an empty preset list. To preserve known-good presets, copy the value out first, fix the JSON in an editor (`jq .` round-trips), and `localStorage.setItem("shipforge.presets.v1", JSON.stringify(parsed))` it back. See [web_ui.md](web_ui.md) for the preset drawer surface. |
| Two biome packs ship YAMLs with the same stem (e.g. both packs define `forest_canopy.yaml`) and `--list-palettes` only enumerates one without warning | Same root cause as the existing pack-collision row but specific to the cycle-5 biome-pack series: `list_palettes()` globs `palettes/*.yaml` and uses each path's `stem` as the canonical name with no namespacing, so two biome packs that happened to pick overlapping names (`forest_canopy`, `desert_oasis`, `glacier_basin`, ...) silently mask each other in filesystem order — and because biome packs are added in 2-palette batches per cycle, the collision can land in a single commit. | Detect *before* committing a new pack with: `python -c "from pathlib import Path; from collections import Counter; print({k:v for k,v in Counter(p.stem for p in Path('palettes').glob('*.yaml')).items() if v>1})"` — empty dict means no collisions. Wire that into the new-pack PR template / pre-commit check so a colliding stem is caught at author time. If a collision is already in `main`, rename one of the YAMLs (e.g. `forest_canopy_temperate.yaml` vs `forest_canopy_tropical.yaml`) and update the CHANGELOG bullet for the renamed pack. |
